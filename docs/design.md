# 設計メモ

要件定義書 v1 の「ポートフォリオで語れること」に対応する、設計判断とその理由。

## 全体

```
data/source/*.json ──► cverse-cli build ──► web/public/data/
 （収集・名寄せ済み）      （検証・生成）        ├ graph.bin     CSR バイナリ
                                               ├ index.json    番号 → ID・表示名
                                               ├ search.txt    検索キー
                                               ├ nodes/<k>.json 詳細パネル用シャード
                                               └ meta.json
ブラウザ: メインスレッド（React + Sigma.js）⇄ Web Worker（cverse-core の WASM）
```

- **サーバーを持たない。** 閲覧時は静的ファイルだけを読む。経路探索も近傍抽出もブラウザ内で完結する
- **中核は 1 つの Rust クレート。** `cverse-core` は I/O を持たず、CLI（ネイティブ）と WASM の両方から使う。
  データを書く側と読む側が同じ型・同じバイナリ形式を共有するので、形式がずれない
- **Worker との境界は数値配列。** WASM は `Uint32Array` を返し、JSON を経由しない。WASM 側にパーサが要らず、
  バイナリも小さい（約 257 KB、gzip 後 約 110 KB）
- **詳細データはシャード分割。** 仕様は「ノードごとの JSON 分割」だが、1 ノード 1 ファイルだと数万ファイルになり
  Cloudflare Pages のファイル数上限に当たる。ID の FNV-1a ハッシュで束ね（1 シャード約 120 ノード）、必要なシャードだけ読む

## 最短経路（F-10）

| モード | 手法 | ねらい |
|---|---|---|
| 最短 | 双方向 BFS | 重みなしグラフの最短。両端から広げて探索量を減らす |
| 主役のみ | 双方向 BFS ＋「主役の登場だけ辿る」絞り込み | ハブ作品の脇役経由を除く |
| 主役を優先 | ダイクストラ（主役 1 / 脇役 3 / その他 6） | ホップが増えても「知っているつながり」を選ぶ |

- **双方向 BFS の打ち切り条件。** フロンティアが小さい側を 1 段ぶん丸ごと広げ、相手側の訪問済みノードに触れても
  その段を最後まで調べてから最短の候補を返す。段の途中で返すと 1 ホップ長い経路になりうる。
  乱数グラフ 30 個 × 絞り込み 4 種 × 40 組で、片方向 BFS と長さが一致することをテストしている
- **ハブ問題。** 登場人物が数百人の作品を通ると誰とでも 2〜3 ステップでつながる。重み付きモードは同じ重みなら
  ホップの少ない方を選ぶ（(重み, ホップ数) の辞書順で最小化）
- **距離の数え方。** 「声優 → キャラ → 作品 → キャラ → 声優」を共演 1 回とし、経路上で作品が連続する区間
  （シリーズをまたぐ場合）は 1 回にまとめる
- **絞り込みは探索にも効く。** 近傍抽出と同じ `Filter` を経路探索でも使う

### 計測

`cverse-cli bench` で、声優どうしのランダムな 1,000 組を計測（リリースビルド、ネイティブ）。

| データ | ノード / エッジ | 片方向 BFS | 双方向 BFS | 主役を優先 |
|---|---|---|---|---|
| サンプル | 385 / 459 | 3.9 µs（訪問 247） | 2.2 µs（訪問 80） | 22 µs |
| 実データ（AniList 300 作品、シーズンをまとめた後） | 12,799 / 21,209 | 204 µs（訪問 11,060） | 16.8 µs（訪問 1,267） | 1.4 ms |
| 合成（ハブ作品 5 本を含む） | 143,297 / 268,594 | 2.15 ms（訪問 141,346） | 0.61 ms（訪問 93,155） | 19 ms |

合成データは MVP の想定（声優 100 人ぶん）より数倍大きい。それでも目標の 500 ミリ秒に対して十分な余裕がある。
実データ（2026-11-21 取得）での平均は、双方向 BFS が 16.8 µs、主役を優先する探索が 1.4 ms（いずれも平均で、個々の探索の上限ではない）。

## 中心切替のレイアウト（F-02, F-03）

普通の力学レイアウトは毎回形が変わり、「声優は上、作品は下」を保証できない。そこで 2 段構えにしている。

1. **決定的な配置。** 中心の種類ごとに、置き場所を計算で決める（`web/src/lib/layout.ts`）
   - キャラ中心: 担当声優を真上、登場作品を真下に固定。同じ作品の他キャラは、その作品と同じ側の弧に寄せる
   - 声優中心: 演じたキャラを円周に、作品ごとの扇形にまとめる。作品はその外側、扇形の中央
   - 作品中心: 主役を内側の円、脇役を外側の円。シリーズの前後作を上に置き、その扇形は空ける
   - 2 段目以降: 親の外側に扇状に開く。小さく薄く描く
2. **制約付きの力学ステップ。** 重なりだけをほどく。中心とアンカーは固定し、他は「元の位置へ戻るばね」と
   「衝突の反発」で落ち着かせる。乱数を使わないので、同じ入力なら同じ絵になる

「1 段目」はグラフ上の距離 1 とは限らない。キャラ中心では同じ作品の他キャラ（距離 2）、声優中心では
キャラの代表作品（距離 2）も 1 段目に含める。どこからでも声優と作品に 1 クリックで戻れるようにするため。
この選び方は `cverse-core` の `view` モジュールにあり、レイアウトは受け取ったスロット（上・下・周囲）に従うだけ。

- **メンタルマップの維持。** 中心を切り替えたとき、前の画面にもいたノードは今の位置から新しい位置へ動かす。
  新しく現れるノードは、親（無ければ新しい中心）が元いた場所から出てくる
- **大量ノード。** 1 段目は主役・人気の順に上位だけ描き（声優・作品中心は 60 件まで）、残りは「他 N 件」にまとめる。
  全件は詳細パネルの一覧で見られる
- **足跡。** パンくずで辿ってきたノードには輪を付け、実エッジが無い組も薄い線で結ぶ

描画は Sigma.js（WebGL）。大きさを座標と同じ単位で持たせ、ズームに合わせて拡大縮小する。
Sigma が描くのは線と、種類の色の形（押した場所の判定もこれで行う）。画像・頭文字・名前の札・担当声優の媒体の注記は、
その上に重ねたキャンバスに描いている。

## 名寄せ（7.3）

`cverse-cli candidates` が候補を JSON で出す。データは書き換えない（人が確認する前提）。

1. 正規化: NFKC、カタカナ → ひらがな、空白・中黒・記号の除去（検索と同じ `normalize`）
2. ブロッキング: 正規化した読みの先頭 2 文字が同じものどうしだけ比べる
3. スコア: 読みの Jaro-Winkler × 0.7 ＋ 隣接ノードの重なり（Jaccard）× 0.3
4. 判定: 0.93 以上は自動統合、0.80 以上は確認待ち
5. 外部 ID が一致すれば同一、両方にあって違えば別物。作品は形態・年が違えば自動統合しない
   （続編は題名も出演者もほぼ同じになるため）。キャラは同名の別人が多いので、グラフ上の証拠が無ければ候補にしない

しきい値と配分は暫定値で、手で正解を付けたサンプルによる適合率・再現率の評価はまだ行っていない。

## 画面の約束

見た目の考え方（色・文字・形・動線）は [design-system.md](design-system.md) にまとめている。ここには動きの約束だけを書く。

- 種類は色と形の両方で区別する（声優 = 橙の丸、キャラ = 青の角丸の四角、作品 = 緑の縦長の四角）
- 画像があればノードと一覧に表示する。読み込めなかったときと画像が無いときは、頭文字のアイコンになる。
  図の上の画像は、形に切り抜いた小さな絵を最近使った順に 480 枚まで持ち、古いものから手放す
- 中心ノード・段数・絞り込み・経路はすべて URL に載る。中心を切り替えるたびに履歴を積むので、
  ブラウザの「戻る」がパンくずを 1 つ戻る動きになる。段数と絞り込みの変更は履歴を積まない。
  「つながりを調べる」は開いたときに 1 回だけ積み、相手や探し方を変えても積まない
- キーボード: `/` で検索、`↑` `↓` `Enter` で選択、`Esc` で閉じる。詳細パネルの一覧はすべてボタンで、Tab で辿って中心を切り替えられる
- スマホ（縦）: グラフは全画面、詳細は下のシート（閉じる・半分・全部の 3 段）。ホバーの代わりに長押しで担当声優を表示。
  横向きでは PC と同じ左右の並びにする
